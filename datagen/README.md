# datagen: synthetic UK documents with gold PII spans

Generator for the training and evaluation data of the Veil redaction model (Mubit task T1:
"Find personal data in one document chunk."). It writes UK-style documents (contracts, bills,
statements, letters, emails, chats, prompts to an AI assistant) together with exact character-span
labels for 13 entity types, chunks them for Mubit, splits them by document and curates the Mubit
round files. Every value is fake: names are random combinations from name lists, identifiers are
generated with valid formats and checksums, nothing is copied from real people.

[Documentation index](../docs/README.md) · [Mubit workflow](../docs/MUBIT.md)

This generator produces files; generating them does not train or deploy a model.
The statistics below describe the recorded seed-42 run, not current live model
performance. Its 6,000-character chunker is separate from the app's 1,400-character
rewrite limit; rebuild/check request sizes for the task you intend to train.

## Run

```bash
cd datagen  # from the repository root
uv sync
uv run pytest -q                                   # generator tests
uv run python -m datagen.generate --n 100000 --seed 42 --out ../data/synthetic
```

`generate` writes everything below and then renders the demo PDFs and the stats. Throughput on an
M-series Mac with 11 worker processes is about 5,000 documents per second, so 100,000 documents
take well under a minute (selection, PDFs and stats add about a minute).

| Flag | Default | Meaning |
|---|---|---|
| `--n` | 100000 | number of documents |
| `--seed` | 42 | master seed; document `i` uses only `Random(f"{seed}:{i}:{attempt}")` |
| `--out` | `../data/synthetic` | output directory (gitignored) |
| `--workers` | CPU count minus 1 | worker processes (output is identical for any value) |
| `--neg-rate` | 0.15 | share of documents with no personal data |
| `--max-chars` | 6000 | max characters per chunk |
| `--round1 --round2 --corrections --eval` | 3000 / 2000 / 200 / 1500 | Mubit file sizes (chunks) |
| `--pdfs` | 30 | demo PDFs to render (0 to skip) |
| `--no-stats`, `--no-copy` | off | skip stats; do not copy stats into `docs/research/.../work/` |

Other entry points:

```bash
uv run python -m datagen.pdf --out ../data/synthetic/pdfs --n 30 --seed 42   # PDFs only
uv run python -m datagen.stats --out ../data/synthetic                       # stats.md (+ copy to research notes)
uv run python -m datagen.audit --docs ../data/synthetic/docs.jsonl --limit 20000   # label leak audit
uv run python -m datagen.samples --data ../data/synthetic --out samples        # committed-safe sample
```

To generate more later, rerun with a larger `--n` and the same seed: documents 0..n-1 are identical,
splits depend only on `(seed, doc_id)`, so existing documents keep their split.

Document record (canonical format from `CONTEXT.md`):

```json
{"doc_id": "syn-000001", "source": "synthetic", "doc_type": "tenancy_agreement", "language": "en",
 "license": "synthetic: generated by Veil datagen, contains no real personal data",
 "text": "...", "entities": [{"start": 10, "end": 30, "text": "Oleksandra Kovalenko", "type": "PERSON"}],
 "split": "train",
 "meta": {"template_id": "...", "variant_id": "...", "negative": false,
          "hard_cases": [{"kind": "common_word_name", "start": 10, "end": 14}],
          "keep_traps": [{"kind": "amount", "start": 50, "end": 59, "text": "£1,250.00"}],
          "entity_refs": ["p1", null], "norm_hash": "...", "skeleton_hash": "...", "n_chunks": 1,
          "near_dup": false, "near_dup_of": null, "max_jaccard_prev": 0.12, "skeleton_dup": false,
          "seed": 42, "attempt": 0}}
```

`entity_refs[i]` groups spans of the same person (`p1`), so `Oleksandra Kovalenko`, `Ms Kovalenko`
and `Oleksandra` can be checked for consistent placeholders. Chunk record:
`{"doc_id", "chunk_id": "syn-000001-c00", "text", "entities" (offsets relative to the chunk), "split",
"doc_type", "meta": {"session_id": "doc-syn-000001", "chunk_index", "n_chunks", "char_start", "char_end",
"negative", "hard_cases", "keep_traps", "entity_refs", "template_id", "variant_id", "skeleton_hash"}}`.

## How documents are built

`core.py` assembles each document from a flat list of segments: plain text, `E(text, type)` entity
values, `K(text, kind)` keep traps, and hard-case region markers. `render()` walks the list once and
records offsets as values are inserted. Nothing is searched for or replaced afterwards, and noise
(typos, lower casing, PDF artefacts) is applied to the segments before rendering, so spans stay exact.
Generators live in `src/datagen/doctypes/` and register with a weight; `generate.py` picks a negative
document with probability 0.15, then a type by weight.

| Module | Doc types (positive weight / negative weight) |
|---|---|
| `prompts.py` | `ai_prompt` (20 / 40): 27 task kinds (complaint rewrite, landlord email, bank detail check, HMRC letter, form fill, translation, reference, card dispute, GP request, bill splitting, address formatting, SAR, birthday, parking appeal, CV help, payslip question, chat summary, tenancy application, cancellation, sick note, incident statement, DVLA/passport, neighbour note, call notes, guest list, email signature, hardship letter) |
| `messages.py` | `chat_messages` (12 / 15; WhatsApp, SMS, Slack, Teams), `email_thread` (9 / 10; headers, signatures, Gmail and Outlook quoting), `support_ticket` (6 / 6; Zendesk, Freshdesk, Jira, web form, live chat), `meeting_notes` (4 / 8) |
| `contracts.py` | `tenancy_agreement` (4 / 4; AST England, periodic, Wales occupation contract, Scotland PRT), `employment_contract` (3 / 4), `nda` (2 / 3), `service_agreement` (2 / 3), `engagement_letter` (3 / 0; solicitor, accountant) |
| `finance.py` | `invoice` (4), `utility_bill` (3), `phone_bill` (2.5), `bank_statement` (3.5), `payslip` (3) |
| `letters.py` | `insurance_claim_letter` (3), `gov_letter` (3 / 4; council tax, HMRC, DVLA, passport), `medical_letter` (3 / 3; GP and hospital, clinical content generic) |
| `people_docs.py` | `cv` (3), `hr_form` (3; new starter form) |

Short messages (`ai_prompt`, `chat_messages`) are about 37% of documents and half of all documents
are under 600 characters, because most real traffic is user prompts. Lengths run from one-sentence
prompts to 17,000-character tenancy agreements.

Shared building blocks: `names.py` (people from 10 origin pools: UK from Faker en_GB, Ukrainian,
Polish, Indian, Nigerian, Irish with fadas, Pakistani, Chinese, Welsh/Scottish, other European; name
surface forms; lazily generated identifiers per person), `world.py` (70 UK towns with real postcode
areas, streets, flats and buildings, 35 synthetic client organisations each with its own CUSTOM id
formats, public company lists, statutes, places, products, keep-trap helpers), `ids.py` (identifier
generators and validators), `noise.py` (typos, casing, PDF artefacts).

## Labelling conventions (the contract every generator follows)

Spans are Python string offsets into `text`; `text[start:end] == span.text`; spans never overlap;
spans never start or end with whitespace.

| Type | What is inside the span | What stays outside |
|---|---|---|
| PERSON | Any mention of a private individual: full name, first name only, surname only, nickname, initials (`OK`, `JS`), `O. Kovalenko`, `KOVALENKO, Oleksandra`, names in greetings and signatures, display names in email headers, payee names in bank transactions (`J SMITH`), a sole trader's own name inside a trading name (`Sarah Jones` in `Sarah Jones Photography`) | Titles (`Mr`, `Dr`, `Mrs.`): `Dear Mr [Patel]`. Possessive `'s`: `[Kovalenko]'s`. Role words (`the Tenant`, `Mum`). |
| ADDRESS | A specific postal address: flat/house number or building name, street, locality, town, county. A multi-line block is ONE span that contains the newlines. Applies to every postal address in the document, whoever it belongs to (person, small firm, letting agent) | The postcode (own span), the country, `c/o` (the c/o person's name is its own PERSON span). A street name with no number used as a place (`the Oak Road works`) is a keep trap. A town on its own (`I live in Leeds`) is not labelled. In `> `-quoted email replies a multi-line address becomes one span per line, so no span contains a quote marker. |
| POSTCODE | A full UK postcode (`LS6 2AB`, `ls62ab`) wherever it appears, also on its own | Outward code alone (`the LS6 area`) |
| EMAIL | The whole address | Angle brackets, `mailto:`. A name inside the local part is not a separate PERSON span |
| PHONE | The number as written, including `+44`, `(0)`, brackets and spaces | `Tel:`, extensions |
| BANK_ACCOUNT | 8-digit UK account number (`12345678`, `1234 5678`); the last 4 digits when the rest is masked (`account ending [0637]`) | A utility, telecom or SaaS "account number" is CUSTOM, not BANK_ACCOUNT |
| SORT_CODE | `20-45-77`, `20 45 77`, `204577` | |
| IBAN | The whole IBAN, compact or in groups of 4 (one span; the embedded sort code and account are not separate spans) | BIC/SWIFT codes (`BARCGB22`) are kept |
| CARD | Full card number (Luhn-valid; Visa and Mastercard 16 digits, Amex 15) in any grouping. Partial: only the visible digits (`ending [4821]`, `**** **** **** [4821]`) | Expiry dates, the word `ending`, mask characters. No CVVs are generated |
| NI_NUMBER | `AB123456C`, `AB 12 34 56 C`, `AB 123456 C` | |
| DOB | A date of birth in any of 11 formats, also a birthday without the year (`turns 30 on [14 March]`) | Ages, all other dates |
| ID_DOC | Government identity numbers: passport (9 digits), driving licence (16 characters), NHS number (10 digits, mod 11). The NHS number is ID_DOC because it is a national number issued to the person, not an organisation's own reference | Issue numbers, expiry dates |
| CUSTOM | Identifiers that key a person's or client's record at an organisation: client codes (`CL-20931`), matter numbers (`M/2024/118`), policy numbers, claim references, customer/account numbers at utilities, telecoms and SaaS, tenancy references, employee and payroll numbers, hospital/patient numbers, HMRC UTR, council tax account references, parking PCN numbers | Identifiers of a document or transaction rather than a person: invoice, order, ticket and bill numbers, transaction IDs, clause numbers, VAT and company registration numbers, employer PAYE references, tax codes (`1257L`). These are keep traps |

Decisions worth knowing:
- **Company names that contain a surname** (`Patel & Sons Ltd`, `Smith and Jones LLP`): registered
  companies are organisations, so they are NOT labelled (keep trap `company_with_person_name`). A sole
  trader's trading name is the person's own name, so the name part IS labelled PERSON.
- **Institutions named after people** (`Taras Shevchenko National University`) are not labelled.
- **Contact details of organisations** (letterhead and registered-office addresses, office and helpline
  numbers, generic mailboxes of firms, councils, NHS trusts) are labelled like any other address, phone or
  email. Reason: the model cannot reliably tell a small firm or sole trader from a company, a missed
  personal number is a leak, and a redacted office number costs little. Large public companies appear
  by name only. **Open conflict:** `docs/research/.../work/hard-cases.md` items 38 and 47 propose the
  opposite (registered office and organisation helplines = keep). If the team adopts that rule, these
  spans are easy to find: they are the ADDRESS / POSTCODE / PHONE / EMAIL spans whose `entity_refs`
  value is `null` (people's details always carry a person ref), except numbers in `phone_bill` call
  lists and `utility_bill` supply addresses, which are personal and must stay labelled. In the 100k run
  these organisation spans are 30% of ADDRESS, 31% of POSTCODE, 13% of PHONE and 1.4% of EMAIL spans.
- **VAT numbers** (checksum-valid): a company's VAT number is a keep trap; a sole trader's VAT number
  identifies the person and is labelled CUSTOM (hard case `sole_trader_vat`).
- **HMRC UTR** is CUSTOM and carries a valid HMRC check digit (first digit). NHS numbers are 60% in the
  `999` range NHS England reserves for test data and 40% in other ranges, so the prefix is not a cue.
- **Already redacted text** (`[PERSON_1]`, `[ADDRESS_1]`) and template fields (`[Tenant name]`) are
  keep traps (`placeholder`), so the model learns not to re-label placeholders.
- **Partial numbers**: only the visible digits are labelled, with the type of the full identifier.
- **Invoice numbers** and similar document references are not personal and are kept.

### Keep traps (never labelled; recorded in `meta.keep_traps`)
`amount`, `date` (tenancy start, invoice date, appointment), `public_company` (Tesco, British Gas,
HSBC, HMRC, NHS trusts, councils), `company_name`, `company_with_person_name`, `org_name`,
`product` (tariffs, phones, accounts), `clause_number`, `statute`, `doc_reference`, `place_name`
(`the Rose Garden`, `the Oak Road works`, `Victoria Park`), `common_word` (`we will`, `grace period`,
`the bill`, `in good faith`), `placeholder` (`[Your Name]`), `relationship_word` (Mum, Landlord),
`company_number`, `vat_number`, `bic`, `tax_code`, `employer_reference`, `named_storm`, `system_text`.

### Hard cases (planted on purpose; recorded in `meta.hard_cases` with offsets)
Names: `common_word_name` (Will, Rose, Mark, Grace, Hope, May, Bill, Joy, Faith, Frank ...),
`non_english_name`, `transliteration_variant` (Oleksandr / Alexander), `greeting_name`,
`signature_name`, `signature_only`, `initials`, `possessive`, `same_person_3_ways` (computed: one
person written in 3 or more surface forms), `name_in_email`, `name_in_transaction`,
`name_in_page_header`, `lowercase_entity`, `sole_trader_name`.
Addresses: `multiline_address`, `flat_number`, `care_of_address`, `address_in_table`, `supply_address`.
Numbers: `partial_number`, `account_next_to_amount` (computed: a bank or card number within 25
characters of `£`/`GBP`), `spaced_identifier`, `custom_org_id`, `partial_dob`, `dob_near_dates`.
Layout: `table_layout`, `quoted_reply`, `pdf_header_footer`, `pdf_hyphenation`, `pdf_double_space`,
`pdf_column_break`.

## Identifier validity (all checked by tests on every generated span)

| Type | Generation and check |
|---|---|
| POSTCODE | real outward codes for 70 towns and London districts, inward `9AA` from the allowed letter set (no C I K M O V); validated with the full Royal Mail pattern |
| NI_NUMBER | first letter not D F I Q U V, second not D F I O Q U V, prefixes BG GB KN NK NT TN ZZ excluded, suffix A-D |
| SORT_CODE / BANK_ACCOUNT | bank-typical sort code prefixes, 8-digit accounts |
| IBAN | `GB` + mod-97 check digits + real 4-letter bank code + the person's own sort code and account |
| CARD | Visa 16, Mastercard 16 (51-55 and 2221-2720), Amex 15; Luhn check digit |
| PHONE | mobiles (35% in the Ofcom drama range 07700 900xxx) in 7 written styles; landlines with real area codes (many in Ofcom drama ranges) in 4 styles |
| ID_DOC | passport 9 digits; DVLA licence 16 characters built from surname, birth decade, month (+50 for women), day, year digit, initials, check letters; NHS number with mod-11 check |
| DOB | 11 formats (`14/03/1987`, `14 March 1987`, `14th March 1987`, `1987-03-14`, `14.03.87` ...) |
| CUSTOM | per-organisation patterns, e.g. `CL-#####`, `M/{yyyy}/###`, `MMH-########`, `CLM-{yy}-######` |

## Duplicates and diversity

- Exact duplicates (case- and whitespace-insensitive text hash) are regenerated with the next sub-seed,
  so the output has none.
- `skeleton_hash`: the text with entities replaced by their type, digits zeroed, case and spaces
  folded. Identical skeletons mean "same document apart from personal values and numbers".
- Fuzzy near-duplicates (`dedup.py`): MinHash (64 permutations, LSH 16 bands x 4 rows) over word
  3-grams of the skeleton. A document is flagged `near_dup` when its estimated Jaccard similarity with
  any earlier document is at least 0.8. Flagged documents stay in `docs.jsonl` but are never selected
  for the Mubit files. `meta.template_id` and `meta.variant_id` (template plus the layout and wording
  choices made) are recorded for every document; stats report the number of distinct variant ids.

## Chunker (`chunker.py`)

Chunks of at most 6,000 characters (about 1,500 tokens). The cut is the last paragraph break in the
final 60% of the window; failing that a line break, a sentence end, then a space. A candidate cut is
rejected if it falls strictly inside an entity span or a keep-trap span, so the boundary moves back to
an earlier safe break; with no safe break at all the cut moves to the start of the span it would
split. Leading and trailing whitespace is trimmed, offsets are relative to the chunk, hard-case
regions are clipped to the chunk, and chunk ids are `<doc_id>-cNN`. A run fails if any span is lost.

## Splits and Mubit round files

Splits are by document: `split_for(doc_id, seed)` hashes the pair into eval 5%, corrections 2%,
fresh 10%, train 83%. Every chunk inherits its document's split.

Selection (`select.py`) works on a light chunk index and is deterministic:
- **Round 1 (3,000 train chunks) and round 2 (2,000 fresh chunks)**: quota-constrained stochastic
  greedy coverage. Quotas give each doc type an even share (water-filling: a type with too few
  candidates gives its share away; hard cap 1.3x the share). At each step 192 random candidates are
  scored and the best is added. The score is doc-type quota pressure + entity-type coverage (rare types
  such as IBAN and ID_DOC gain more while under-represented) + hard-case coverage + template-variant
  novelty + length-bucket novelty + a negative term that steers negatives to about 15%. Constraints:
  one chunk per document, no repeated skeleton, no two selected chunks with estimated Jaccard >= 0.7,
  no documents flagged as near duplicates.
- **Corrections (200)**: same loop on the corrections split, positives only, with extra weight for
  CUSTOM ids and for the number of distinct hard cases (cap 1.5x the even share per doc type).
- **Eval (about 1,500)**: whole documents (all chunks of a document, so leak rate per document and
  zero-leak documents are measurable), doc types taken round-robin until the chunk budget is full.

## Demo PDFs (`pdf.py`)

30 documents of 16 document-like types rendered to A4 with fpdf2 (Georgia for contracts and letters,
Arial for bills and forms, Courier for column-aligned statements and bills, real tables for markdown
tables, page footers). Next to each PDF, `NN_type.gold.json` holds the source text and spans, the text
extracted back with pdfplumber, the gold spans re-aligned to the extracted text, the spans that could
not be found, and a text similarity score. `pdf_report.json` summarises the mismatch rate.
Expected extraction differences: wrapped lines insert newlines (spans are matched whitespace-flexibly,
and `whitespace_changed_rate` counts spans whose exact text changed), the real page footer
(`Page 1 of 3`) is added, markdown markers (`#`, `|`, `**`) disappear, table cells are joined by
spaces, and tabs become spaces.

## Validation, tests and audit

`validate.py` runs on every document during generation (a failing document is regenerated with the
next sub-seed): span text equals the slice, no overlaps, types in the allowed set, no padded spans,
checksums and formats (Luhn, mod-97, NI rules, sort code, postcode, phone, passport / licence / NHS),
partial numbers are 4 digits, keep traps never overlap entities, negatives have no entities, chunk
text equals the document slice and relative offsets are right.

`uv run pytest -q` covers: identifier generators and validators (known valid and invalid values),
the builder, every doc type (120 documents each, positives and negatives), determinism per type and
for the whole pipeline (same seed with 1 and 3 workers gives byte-identical files; another seed
differs), chunker (spans never cut at 6,000 / 1,500 / 600 chars, hard-cut fallback), split
disjointness and shares, Mubit file constraints, stats, the PDF round trip, and a label leak audit.

`audit.py` looks for personal data outside every gold span and keep trap: regexes for emails,
postcodes, UK phones, sort codes, NI numbers, IBANs, 8+ digit runs, numbered street addresses, and
dates after "DOB / born"; and every first name and surname from the generator's own pools. On 20,000
documents it finds nothing except `Shevchenko` inside the institution name above.

## Known limitations

- Synthetic distribution: English UK documents only, built from templates and phrase pools. The
  model will see real documents with layouts, wording and errors we did not imagine. Numbers measured
  on this data do not prove performance on real documents.
- Template families are finite: long documents of one type share clause wording (MinHash similarity
  0.5 to 0.7 between two tenancy agreements is normal), so a model can partly learn the templates.
- Postcodes have real outward codes but the locality and outward code are not geographically matched
  (for example `Brixton, London NW7`), and landline area codes are not tied to the town.
- Vehicle registrations, CVVs, URLs and social handles (LinkedIn) are not generated, because they are
  not among the 13 types; a real document can contain them.
- Names are labelled only where we put them; a name in an org or institution name is deliberately
  kept, which is a judgement the teacher model may not share.
- PDFs are rendered from our own text, so extraction is cleaner than scanned or designed PDFs (no
  OCR errors, no multi-column layouts beyond the simulated column breaks).
- Some cross-field realism is loose (an emergency contact's relationship is not tied to age, phone
  area codes do not match towns, a few dates in quoted emails can be later than the reply).
- No paraphrasing by an LLM (T3) was used; all wording is from hand-written pools.
- Research hard cases from `hard-cases.md` that are NOT generated: names that are cities (Florence),
  obfuscated or line-wrapped emails, phone numbers split or spelled out in speech, non-UK phone numbers,
  NINO without suffix, DOB in words, licence with issue number, 10-digit or roll-number accounts,
  IDs shaped like postcodes, references built from a surname, ligatures and no-break spaces, values cut
  by a chunk edge (our chunker never cuts a span, so this only happens in real traffic), BFPO addresses.
- Card expiry dates and CVVs are not generated (research proposes labelling them CARD; undecided).
